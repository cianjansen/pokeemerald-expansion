# Project Spec

## What this is

A personal Pokémon Emerald romhack built on top of [pokeemerald-expansion](https://github.com/rh-hideout/pokeemerald-expansion) (pret decomp + community expansion). Custom content is being added incrementally, largely by Claude Code agent sessions. This file exists so a fresh agent session has enough context to keep working without re-discovering the whole project from scratch.

Custom region so far: **Ouderkerk** (Dutch-themed), maps prefixed `data/maps/Ouderkerk*`. Content and NPC dialog for this hack are written in Dutch, often as in-jokes for a specific friend group.

**This project is worked on from multiple machines** (as of 2026-08-16: a Mac and a Windows/WSL2 machine), with git used to sync between them. Don't assume the toolchain/OS described in a past session's notes still matches the one you're running in now — check "Toolchain" below for the current session's actual platform, and verify commands work before trusting stale platform-specific paths. **Also `git pull` before starting work** — this file and the maps below get edited from both machines, and stale local state has caused real lost-work incidents this project (see Status).

## Debug options

Build-time toggles for testing content quickly, off (`0`) by default so a plain `make`/`./reload` never ships debug content. Enable by passing the variable on the command line — nothing to edit in source:

```
./reload OUDERKERK_DEBUG_FATBIKE=1 OUDERKERK_DEBUG_BLAZIKEN=1
# or on Windows/WSL2: powershell -File reload.ps1 OUDERKERK_DEBUG_FATBIKE=1 OUDERKERK_DEBUG_BLAZIKEN=1
# or a raw make invocation: make OUDERKERK_DEBUG_FATBIKE=1 ...
```

- **`OUDERKERK_DEBUG_FATBIKE`**: New Game starts with `FLAG_GOT_FATBIKE` already set and `ITEM_MACH_BIKE`/`ITEM_ACRO_BIKE` already in the bag — skips needing to beat Jonas to get past the `OuderkerAmstel` bike-blocker. Implemented directly in C, in `CB2_NewGameSkipIntro` (`src/overworld.c`) right after `NewGameInitData()`.
- **`OUDERKERK_DEBUG_BLAZIKEN`**: grants a Lv.100 BLAZIKEN (SWIFT) the moment New Game drops the player in `Ouderkerk_MargrietHouse_2F` (Margriet's room), instead of via the starter-ball pick — the starter scripts (`Ouderkerk_MargrietHouse_1F/scripts.inc`) no longer touch it at all. Implemented as a `MAP_SCRIPT_ON_LOAD` on that room (`Ouderkerk_MargrietHouse_2F/scripts.inc`), gated on `FLAG_DEBUG_GOT_BLAZIKEN` so re-entering the room doesn't grant it again. Uses the `givemon` script command, which is why this one's a map script rather than plain C like the fatbike toggle — `givemon` compiles to `callnative ScrCmd_createmon`, a script-VM-only native, not something safely callable as a bare C function from `CB2_NewGameSkipIntro`.

**How the plumbing works** (relevant if adding another one of these): both variables get `?=` defaults of `0` in `Makefile` right where `CPPFLAGS` is built, then get appended as `-DOUDERKERK_DEBUG_X=$(OUDERKERK_DEBUG_X)`. Since `CPPFLAGS` also feeds the `.inc`/`.s` script preprocessing pipeline (not just `.c` files), `#if OUDERKERK_DEBUG_X` works in both C source and map scripts — see the two toggles above for one example of each. `./reload`/`reload.ps1` just forward their own args straight through to `make`, so no separate plumbing was needed there.

## Repo layout notes

- This is a standard pret-style decomp. Source of truth for maps is `data/maps/<MapName>/map.json` and `data/layouts/layouts.json`.
- `header.inc`, `events.inc`, and `connections.inc` inside each map folder are **auto-generated from map.json and are gitignored** — never hand-edit them, edit `map.json` instead.
- To regenerate a map's `.inc` files after editing its `map.json` (without doing a full `make`):
  ```
  ./tools/mapjson/mapjson map emerald data/maps/<MapName>/map.json data/layouts/layouts.json data/maps/<MapName>
  ```
- To sanity-check a map/script change compiles without doing a full ROM build (the full `make` may be broken locally due to an unrelated missing-newlib-headers toolchain issue — see "Known environment issues" below):
  ```
  make build/emerald/data/map_events.o
  ```
  This runs the real preproc → cpp → as pipeline over all `scripts.inc`/`map.json`-derived data and will fail loudly on bad script/text syntax.

## Conventions used in this hack

- **NPC scripts**: standard pret macros — `lock`, `faceplayer`, `msgbox ..., MSGBOX_DEFAULT`, `goto_if_set`, `setflag`, `release`, `end`. Look at existing `data/maps/*/scripts.inc` files for the idiom.
- **"Talk once, then different dialog forever after" pattern**:
  ```
  EventScript_Foo::
      lock
      faceplayer
      goto_if_set FLAG_X, EventScript_FooRepeat
      msgbox Text_FooFirst, MSGBOX_DEFAULT
      setflag FLAG_X
      release
      end

  EventScript_FooRepeat::
      msgbox Text_FooRepeat, MSGBOX_DEFAULT
      release
      end
  ```
- **Flags for this kind of one-off story/dialog state**: reserved from the `FLAG_UNUSED_0x0xx` pool in `include/constants/flags.h` — rename one of those defines in place (don't delete the surrounding block, don't reuse a flag that's already meaningful elsewhere). Give it a descriptive name (e.g. `FLAG_TALKED_TO_MARGRIET`).
- **Object event placement**: `"flag": "0"` on an object_event means it's always visible (no hide-flag). Use `elevation` matching the metatile it stands on (check `data/layouts/<Layout>/map.bin` / the layout's tile grid if unsure — don't guess).
- **Dialog text**: `.string` macro. `\n` = line break within the same textbox, `\l` = further line within the same (3-line) box, `\p` = new textbox page (player presses A), `$` = end of string. Keep each line under ~38 characters. `charmap.txt` supports Dutch accented characters (`é`, `ë`, `ï`, etc.) if needed. In-game proper nouns/names are conventionally written in caps (e.g. `MARGRIET`, `POKéMON`).
- **Picking an `OBJ_EVENT_GFX_*` sprite for a new NPC — check it's actually usable on Emerald first.** This is an Emerald build (`IS_FRLG` false), but the graphics data for FRLG/Kanto-exclusive character sprites (e.g. `OBJ_EVENT_GFX_CLERK`) still compiles in unconditionally — no `#if IS_FRLG` guard, so nothing stops you from placing one, and the struct itself (OAM size, palette tag, pic table) looks completely normal on inspection. It still crashes the game on map load (confirmed by bisection: `OBJ_EVENT_GFX_CLERK` alone in an otherwise-empty room reproduced it 100% of the time; swapping to `OBJ_EVENT_GFX_WOMAN_2` fixed it instantly, same map, same everything else). The exact mechanism was never fully root-caused — comparing the graphics struct field-by-field against known-good sprites showed nothing — so treat any FRLG-exclusive sprite as unsafe by inference, not just the ones caught so far. **Before using a graphics ID, run:**
  ```
  grep -rl '"<OBJ_EVENT_GFX_NAME>"' data/maps/*/map.json | grep -v _Frlg
  ```
  If that comes back empty, the sprite has never been used on a non-Kanto map in this whole codebase — don't use it; pick something with real Emerald-side precedent instead (e.g. grep shows plenty of hits for generic `OBJ_EVENT_GFX_WOMAN_*`/`MAN_*`/`BOY_*`/`GIRL_*`). **`OBJ_EVENT_GFX_BIKER` is now a confirmed member of this unsafe family too** (hit for real on `Ouderkerkerplas`'s `JONAS` placeholder — same crash signature, fixed by switching to `OBJ_EVENT_GFX_CYCLING_TRIATHLETE_M`, which has real precedent on Route110/Route119/JaggedPass).
- **Reusable free-heal NPC**: `Common_EventScript_Healer` (in `Ouderkerk/scripts.inc`, alongside the other `Common_EventScript_*` shared logic) is a talk-to-heal NPC — shows one flavor line then `special HealPlayerParty`. It's map-agnostic (doesn't reference its own `local_id`), so reusing it on a new map is just: drop an object_event with `graphics_id: "OBJ_EVENT_GFX_SCIENTIST_1"` (confirmed safe on Emerald) and `"script": "Common_EventScript_Healer"` — no new script needed, no per-map wrapper. **Give it a map-prefixed `local_id` every time (e.g. `CMROUTE1_HEALER`), never the bare name `HEALER`** — two maps both using `"local_id": "HEALER"` collided for real (see Status), because `local_id` compiles to a plain global `#define`, not something map-scoped (same footgun as the map-cloning checklist below, just hit here independently). Placed so far on `Ouderkerkerplas` (little dock in the middle of the lake) and `CMroute1`. Intended to keep recurring on future routes as a "Healer" character.

### Cloning an existing map as a starting point for a new area

Porymap's "duplicate map" (and hand-copying a `map.json`) copies every symbolic name as-is. Names aren't auto-uniquified, so a cloned map silently keeps referencing/sharing the original's identity in a few places. Go through all of these on the clone before treating it as done — none of them cause a build error if skipped, which is exactly why they're easy to miss:

- **`local_id`** on object_events: becomes a `#define LOCALID_X <n>` in the auto-generated `include/constants/map_event_ids.h`. It's a plain macro, not scoped to the map, so if two maps reuse the same `local_id` name with *different* numeric positions, whichever is defined later in that generated header silently wins everywhere — including in the *original* map's own scripts. This showed up for real: `Ouderkerk` (cloned from `LittlerootTown`) and `LOCALID_LITTLEROOT_RIVAL`/`LOCALID_LITTLEROOT_BIRCH` colliding, breaking LittlerootTown's own intro script. Fixed by renaming the clone's `local_id`s to be map-specific (`LOCALID_OUDERKERK_*`). **Tell:** `-Wall -Werror` build logs a `'LOCALID_X' redefined` warning (see "Toolchain" for how to actually get a build that surfaces this). **Before renaming a colliding one, `grep -rn` the name repo-wide, not just the map's own `scripts.inc`** — a *shared* script (e.g. `data/scripts/players_house.inc`) can intentionally hardcode one `local_id` name used by multiple maps by design (matching indices on purpose, e.g. two gender-variant house maps). Renaming away from under that isn't a warning, it's a hard assembler error (`non-constant expression in ".if" statement`, because the now-undefined symbol isn't a number anymore). If you hit that, the fix is usually to have each map's own entry-point script pass its correct `local_id` into the shared script via a scratch var (`VAR_0x8008` or similar) instead of the shared script hardcoding a name — see the `LOCALID_PLAYERS_HOUSE_2F_MOM` fix in Status below for a worked example.
- **`flag`** on object_events (the per-object visibility/hide flag): this is a real save-file flag, and reusing the original map's flag name means the two objects share hidden/shown state — toggle one, the other changes too. **No build warning at all for this one.** `Ouderkerk`'s Fat Man/Mom currently still share `FLAG_HIDE_LITTLEROOT_TOWN_FAT_MAN`/`FLAG_HIDE_LITTLEROOT_TOWN_MOM_OUTSIDE` with LittlerootTown's — known, not yet fixed as of 2026-08-15 (see Status below). Give the clone's objects their own flags (reserve fresh ones the same way as the `FLAG_TALKED_TO_MARGRIET` example above).
- **`script`** references on object_events/bg_events/coord_events: cloning doesn't fork the script — the clone's objects keep calling the *original* map's `scripts.inc` symbols (e.g. `Ouderkerk`'s Twin/Fat Man/Mom/sign objects still call `LittlerootTown_EventScript_*`), which means the clone shows the original's text/logic verbatim (still says "LITTLEROOT", may reference the original map-specific vars/state) until you give the clone its own scripts and point these at them.
- Lower priority / only matters if the area needs to feel distinct: `region_map_section` (controls the Town Map / Fly list name), `music`.

## Toolchain

**This project is actively built from two machines, not a one-way migration** — a Mac and a Windows/WSL2 machine, both still in regular use as of 2026-08-16 (an earlier version of this section framed the Mac setup as "superseded"; that was wrong — a full multi-hour session's worth of work, including the FRLG-sprite crash hunt above, happened successfully on the Mac *after* that note was written). Figure out which machine you're actually on and use the matching subsection below; don't assume from a past session's notes.

### Windows + WSL2 (Ubuntu)

- The canonical repo clone lives inside the WSL2 Linux filesystem at `~/decomps/pokeemerald-expansion` (i.e. `\\wsl.localhost\Ubuntu\root\decomps\pokeemerald-expansion` from Windows) — **not** under `/mnt/c/...` — because building against the Windows-mounted filesystem from WSL2 is drastically slower.
- Build toolchain is plain Ubuntu apt packages (no devkitPro needed on this platform): `build-essential binutils-arm-none-eabi gcc-arm-none-eabi libnewlib-arm-none-eabi git libpng-dev python3`, already installed in the `Ubuntu` WSL distro. `wsl -d Ubuntu` defaults to the `root` user (set via `/etc/wsl.conf`, `[user]\ndefault=root`) — the distro's interactive first-run "create a UNIX user" wizard can't be driven non-interactively, so this sidesteps it.
- To build from Windows PowerShell:
  ```
  wsl -d Ubuntu -- bash -c "cd ~/decomps/pokeemerald-expansion && make -j$(nproc)"
  ```
  or just from inside a WSL shell: `cd ~/decomps/pokeemerald-expansion && make -j$(nproc)` (16 cores available on this machine).
- **`reload.ps1`** (repo root) is the Windows equivalent of the old Mac `./reload`: runs the WSL build, then launches Windows-native `mGBA.exe` (installed via `winget install JeffreyPfau.mGBA`, at `C:\Program Files\mGBA\mGBA.exe`) pointed at the ROM via its WSL UNC path, then prints `git status --short`. Run it from Windows PowerShell:
  ```
  powershell -File \\wsl.localhost\Ubuntu\root\decomps\pokeemerald-expansion\reload.ps1
  ```
  Unlike the old Mac script, this one does **not** have the Porymap no-op-rewrite-discarding step (see Mac notes below) — not yet ported, so watch `git status` after Porymap saves for reorder-only noise on this platform.
  A clean build has **zero** warnings — treat any `redefined` warning in the log as a real bug to fix (see the map-cloning checklist above), not noise to ignore.
- For a quick syntax check of just map/script data without a full build (works from either a WSL shell or via `wsl -d Ubuntu -- bash -c "..."`):
  ```
  make build/emerald/data/map_events.o
  ```
- No emulator CLI is set up for automated in-game verification — `mGBA.exe` is GUI-only. `reload.ps1` opens it with the new build automatically; actually playing through a change still means clicking through by hand.
- The `tools/mapjson/mapjson event_constants` mode (regenerates `include/constants/map_event_ids.h` from every map.json) breaks/errors when passed the full ~943-file list as separate args — don't invoke it directly for that; a full `make`/`reload.ps1` regenerates it correctly (it's gitignored, auto-generated, never commit it). If you need to hand-verify a `local_id` rename without a full build, it's safe to edit that generated header directly for local testing.

### Mac

- The `arm-none-eabi-gcc` on `PATH` (Homebrew's) is missing newlib (`string.h`, `alloca.h`, etc.) and **cannot build this project** — a plain `make` fails immediately with `fatal error: string.h: No such file or directory`. Don't try to fix that install; just use the working one below.
- A working toolchain **is** installed at `/opt/devkitpro/devkitARM/bin` (includes newlib). Prepend it to `PATH` (and export `DEVKITARM`/`DEVKITPRO`) for the build:
  ```
  PATH="/opt/devkitpro/devkitARM/bin:$PATH" DEVKITARM="/opt/devkitpro/devkitARM" DEVKITPRO="/opt/devkitpro" make -j"$(sysctl -n hw.ncpu)"
  ```
- `./reload` (repo root) is the edit-build-play loop: it exports `DEVKITARM`/`DEVKITPRO` correctly, discards Porymap no-op rewrite noise from `git status`, runs a full `make -j`, then quits/relaunches `mGBA.app` with the freshly built `pokeemerald.gba`.
- **For crash debugging**, launch mGBA directly with logging instead of `./reload`, so you get a persistent log file to grep instead of just watching it happen once:
  ```
  nohup /Applications/mGBA.app/Contents/MacOS/mGBA -C logToFile=1 -C "logFile=/path/to/mgba.log" -l 511 "$(pwd)/pokeemerald.gba" > /dev/null 2>&1 &
  ```
  A real crash shows up as a `[GAME ERROR] GBA Memory: Bad memory Load8: 0x189b189d`-style block right after a `DMA 3 0x03007DA8 -> 0x0600xxxx (8100:0800)` VRAM-clear sequence in the log (that clear is the normal per-map-load screen wipe, not itself a bug — it's what runs *right before* the crash, every time). This is exactly how the FRLG-sprite bug above got bisected: strip a map down to zero objects, confirm it stops crashing, then add objects back one at a time until it reproduces again.
